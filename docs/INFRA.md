# Infrastructure Notes

Facts about the RunPod path that are perhaps not obvious and perhaps had to be learned from a failed run. Read this before changing e.g. `.github/workflows/run-gpu.yml`, `experiments/remote.py`, `scripts/runpod_*.py` or `src/directions/remote.py`. How to dispatch a run is in `README.md`.

## The flow of a run

0. The workflow starts either from a push that modifies the request file `.github/gpu-run.yaml` (its fields are the run parameters; `scripts/runpod_request.py`, standard library only, validates them inside the job) or from a `workflow_dispatch` form (whose inputs are used instead). The push path exists because a session token with git push access may still lack the Actions write permission that `workflow_dispatch` needs (Claude Code web sessions get a narrowed token: pushes succeed, dispatches return HTTP 403 "Resource not accessible by integration"). The `gate` job also resolves the request's `flash_env` so the `run` job's concurrency group (`run-gpu-<flash_env>`) follows the request file rather than a fixed name; two requests with different environments run in parallel. GitHub's `paths` filter matches a force-push even when the request file's content is unchanged (a history rewrite of `fable` started run 34485947980), so a `gate` job compares the file's blob SHA at the push's old and new commits through the contents API and skips the run when they are equal; a manual dispatch always passes the gate.
1. The runner checks `uv lock --check` (the worker builds the shipped tree's venv from the lock), installs only `runpod-flash` and `boto3` into a `.venv`, and stages the **handler-only Flash app**: `scripts/runpod_stage.py` copies `experiments/remote.py` and `src/directions/{remote,__init__,_version}.py` into `.flash-app/` and prints a digest of those files plus the endpoint configuration (GPU tier/type, data center, Flash environment, Flash and Python versions). No experiment code enters the artifact, and Flash's build scan (which imports every module it ships) needs nothing but the standard library and `runpod_flash`.
2. The endpoint is **reused when its handler digest is unchanged**: the last deploy's record (`.runpod-endpoint.json`: endpoint id, URL, digest) is kept in the Actions cache under `runpod-endpoint-<env>-<digest>-<run id>` (restored by prefix, so the newest record for a digest wins), and the runner confirms with `runpod_cleanup.py --exists <id>` that the endpoint is still live in the Flash environment. Otherwise it deletes the previous endpoint, runs `flash deploy` from `.flash-app/`, writes a new record and saves it to the cache. Reuse skips the cleanup + deploy (~1.5 min) and never leaves a stale handler unnoticed: the handler's fingerprint is still reported by every job (`handler_stale`). Verified with the torch/CUDA probe as the request: run 34491839677 took the deploy path (no record, fresh endpoint, record saved; job 3.6 min including the cold start) and run 34492381854, five minutes later, the reuse path (record restored, endpoint live, deploy skipped; job 47 s), each running its own shipped commit.
3. The runner submits one job carrying `git archive` of the commit (always; a job without it is an error on the worker). The worker unpacks the shipped tree to `/app/jobs/<digest>`, builds that tree's venv from its `uv.lock` (torch from the lock, not from the image), and runs the command there with `results/` on local disk. The handler exports `DIRECTIONS_GIT_COMMIT` (the commit the runner shipped) to the command: experiment code should record it in its own run metadata, because a `git archive` tree has no `.git` for `git rev-parse` to read.
4. The child's output streams to the container log, to `results/runner.log`, and to the same file on the volume; the runner tails that file over S3 as it polls (progress shows in the GitHub job log).
5. The results directory is copied to the volume on exit, in `results/run-<GITHUB_RUN_ID>`, the runner downloads it over S3 into `results/remote`, and the workflow uploads as an artifact.
7. Two failure modes seen on 2026-09-21. A worker can stall silently: run 35561562655 stopped writing output 33 min in (its last stage had finished normally) and stayed `IN_PROGRESS` for 47 min with the volume's `runner.log` untouched; nothing bounds a worker's progress, so a run whose log is behind its cadence is cancelled from the Actions UI (`gh run cancel <id>` works with the session's token) and re-requested. And when the RunPod account's credit is exhausted, job submission (`POST <endpoint>/run`) fails with `HTTP Error 402: Payment Required` after the endpoint was reused successfully; the workflow reports it as a failed `run on RunPod` step. Nothing in the pipeline can proceed until credit is added. `scripts/runpod_balance.py` reads the balance (`myself.clientBalance`, read-only key) and `--need <usd>` (or `--hours` with `--rate`) exits 1 unless the balance covers the estimate plus a 50 % margin; check it before every request of more than a few minutes, since a job that runs out of credit mid-run is lost too. The rates in use: RTX 4090 1.10 USD/h, H100 4.79 USD/h.
6. The volume is 50 GB (`DIRECTIONS_VOLUME_GB`) and holds the Hugging Face cache (`HF_HOME=/runpod-volume/hf`), the wheelhouse and every run's results copy. Two 8B-class models plus the results fill it: a third model's download then fails with `OSError: [Errno 122] Disk quota exceeded` after ~8 min (run 35559030152, 2026-09-21). `scripts/volume_cleanup.py`, run as a request's command, reports the usage per model cache and run directory and deletes named model caches and partial (`*.incomplete`) blobs; results copies are the inputs of later comparison runs (`--fv-run`/`--learned-run` paths), so delete only model caches whose runs are finished and downloaded.

## Flash (runpod-flash)

- `flash deploy` is only idempotent through the pickle in `.flash/`, which a fresh runner does not have; a second deploy re-creates the endpoint and RunPod rejects the duplicate template name. Hence the cleanup step, which deletes the environment's endpoint through GraphQL before a (re)deploy; when the endpoint is reused there is no deploy and no cleanup. `flash undeploy` reads the same pickle.
- `flash deploy` builds the directory it runs in (`.flashignore` is no longer honoured). Hence, the handler is staged into `.flash-app/` rather than deployed from the repository root. The build imports every shipped `.py` file (without `__init__.py`) to find the endpoint and errors on any import error, so the staged files must import only the standard library and `runpod_flash`, and package code must not `from . import name` for a name defined in `__init__.py`.
- The staged app has no `requirements.txt`, so nothing is bundled (the experiment's dependencies come from the shipped tree's `uv.lock`, installed by `uv run` on the worker; `uv` and Python 3.11 are on the image). (Note, if the artifact ever bundles deps once more: torch, torchvision, torchaudio and triton are stripped from the bundled deps.)
- FlashBoot restores workers from a snapshot of an earlier boot on the same image, `/app` included, so after a redeploy workers ran the previous build. It is off. Even so, **workers run the previous deploy's artifact when a run starts within ~15 min of the previous deploy** (2026-09-10: runs 34434569577 and 34436082660, each on a freshly created endpoint, each served by a worker whose on-disk fingerprint was the *previous* run's build; run 34434269088, six hours after the deploy before it, was correct). In run 34436082660 all four job attempts over 16 minutes landed on the same container (its `results/` already held the first attempt's run directory), so waiting 90 s between attempts did not help either. The mechanism is inside the worker image's artifact fetch (not in the `runpod_flash` package), presumably a cache with a TTL of the order of tens of minutes.
- Therefore **the job ships its own code**: the runner always sends `git archive` of the checked-out commit (gzipped + base64, ~0.24 MB; `directions.remote.pack_source`) and its SHA-256 in the job input; the handler verifies the digest, unpacks it under `/app/jobs/<digest>` and runs the command there (`uv run` builds that tree's venv from its own `uv.lock`). The deployed artifact contains only the handler (see "The flow of a run"), so there is exactly one code path: a job without shipped source is an error, and the handler's own staleness is reported (`handler_stale`) but harmless. The runner fails, after resubmitting up to `--stale-retries` times with `--stale-wait-seconds` between attempts, only if the worker does not report having run the shipped digest (a handler from before shipped source existed; such a handler rejects the new inputs, which the platform reports as a FAILED job with `unexpected keyword argument 'source_...'`, and the runner treats that as stale too). Before each resubmission the runner asks the API to terminate the answering worker (`podTerminate` with the job's `workerId`, best effort): a stale container was seen answering jobs for 25+ min (run 34437755152, 04:37, still the container first seen at 04:11) despite the 30 s idle timeout, so RunPod evidently restarts the stopped container, `/app` included, rather than creating a new one. The handler accepts and reports unknown inputs, so a runner newer than the handler never produces a FAILED job for that reason.
- A Flash environment name is part of the endpoint template's env, so two environments never collide on template names; run in parallel by giving each request its own `flash_env` (the workflow's `run` job is serialised per resolved `flash_env`, from the request file or the dispatch form). The cleanup only sees the environment it is told (`--env`): an endpoint deployed under another environment name (one `directions-runner` in an environment `fable` survived every `ci` cleanup) has to be deleted from the console or with a full API key.

## RunPod

- `api.runpod.io` (GraphQL and REST v2) answers HTTP 403 to Python's default urllib user agent; the scripts send their own. The API on `api.runpod.ai` does not care.
- REST v2 has no endpoint-management routes; endpoints are managed through GraphQL. A missing Flash app or environment is a GraphQL "not found" error, not a null result.
- GPU tiers are memory classes whose pools mix architectures (`AMPERE_16` holds Ampere and Ada cards; only `ADA_24` is a single card). A host's driver can be older than the lock's torch build: the lock's torch is a CUDA 13 build, a 12.8 host ran the whole pilot on the CPU, 50-170x slower, with `device: auto`. The endpoint requires CUDA >= 13 (`DIRECTIONS_MIN_CUDA`) and the pilot configs pin `device: cuda`.
- The output of a job is not a results channel: one 0.6B pilot was 24 MB encoded and RunPod documents no ceiling. Results arrive through the volume and its S3 API (`https://s3api-<dc>.runpod.io`, region = data center id, bucket = volume id, separate S3 API key). The volume pins the endpoint to its data center.
- For reference, a cold start is ~30-90 s; the uv venv build on the worker ~30 s; a 0.6B fable pilot 42 min on an RTX 4090 (before optimizing and lowering sample size).
- Workers see the host's CPU count (120 on one host) with no cgroup quota; BLAS and torch threads are capped by the CLI (`DIRECTIONS_BLAS_THREADS`).

## Reading a run from outside

- Live: the GitHub job log (tailed from the volume), or the worker's container log (`stream-worker-logs` with the id from `list-endpoint-workers`). From outside the workflow, `scripts/runpod_log.py <run id>` reads the same `runner.log` from the volume (`--follow` tails it, `--list` and `--download` reach the results before the workflow uploads them); it needs `RUNPOD_API_KEY`, `RUNPOD_S3_ACCESS_KEY` and `RUNPOD_S3_SECRET_KEY`, which are also set in the Claude Code cloud environment used for these sessions. GitHub serves a job's log only after the job ends, so this is the only live view a session has; without it a job that never left the queue looks like a long run (below).
- After: the workflow artifact, or `results/run-<id>/` on the volume over S3.
- `scripts/runpod_availability.py` prints, per tier, the data centers that currently report stock of that tier's cards (RunPod's `dataCenters.gpuAvailability`, the console's signal; it fluctuates minute to minute and "Low" is the usual reading), by default restricted to the data centers a run can use. Two lists constrain the `datacenter` input, and `scripts/runpod_request.py` validates against their intersection (US-CA-2, US-IL-1, US-MO-2, US-NC-2, EU-RO-1, EUR-NO-1): Flash 1.19 accepts only eleven data centers for a network volume (`runpod_flash.core.resources.datacenter.DataCenter`; any other fails `flash deploy` with a `NetworkVolume dataCenterId` validation error, run 34858497382), and RunPod creates network volumes only in some data centers (the REST error of run 34858770757 lists eighteen; `US-NE-1`, though in Flash's list, is not among them). Check it before requesting a tier other than `ADA_24` or a new data center. A read-only API key is enough for it and for `scripts/runpod_log.py`; the key set in the Claude Code cloud environment is read-only (deleting an endpoint, and Flash's own app queries, return `Unauthorized`), so endpoint cleanup from a session goes through the console.
- A tier can have no worker in the data center: an `ADA_48_PRO` request in `EUR-NO-1` (run 34778958703) and then an `AMPERE_80` one (run 34794257716) each stayed `IN_QUEUE` for the whole 340-minute job timeout without a worker being assigned, and the runner then cancelled them. Only `ADA_24` (RTX 4090) has ever been assigned there. Two causes are possible and the runner cannot tell them apart: no card of that class in the data center, or none whose host driver satisfies `min_cuda_version` (13.0, required by the locked CUDA 13 torch build; A100 and A40 hosts often run older drivers). The queue state is visible only in the live log, so the runner now gives up after `--queue-timeout-minutes` (default 20) of `IN_QUEUE` with status `NO_WORKER`; a worker normally takes a job within a minute or two. At the time, `EUR-NO-1` reported no card of either class at all (availability script above). The endpoints RunPod holds for these deploys have an empty `allowedCudaVersions`, so Flash's `min_cuda_version` is not what filters hosts; a host whose driver cannot run the locked CUDA 13 torch build fails at model load instead (`device: cuda`).
- A second worker is allowed on the endpoint; a probe job can run beside a pilot; the handler runs any `argv`, so a probe can read the volume, the log, or the host's state.
- **PyPI's CDN throttles RunPod workers.** A probe from a worker's image Python (`scripts/probe_bandwidth.py`, run as the request command, no install) measured 55 MB/s to a generic CDN and 16 MB/s to Hugging Face but 0.3 MB/s to `files.pythonhosted.org`, the host every wheel of a fresh environment comes from (2026-09-15 23:30 UTC, EUR-NO-1; workers in US-IL-1 crawled the same way at the same time, and the four-hour install below was the same thing a day earlier). At that rate the 3 GB of a fresh venv take three hours, so the install must not depend on PyPI: `scripts/runpod_wheelhouse.py build` downloads the locked wheels (plus the `uv_build` backend) on a linux x86_64 / CPython 3.11 host, `upload` puts them under `wheels/` on a volume, and the handler, when that directory exists, builds the venv with `uv pip install --no-index --find-links /runpod-volume/wheels` from the lock's export and runs the command with `uv run --no-sync` (`directions.remote.offline_argv`; commands that are not `uv run`, like the probe, are untouched). The wheelhouse must be rebuilt and re-uploaded whenever `uv.lock` changes (the install fails fast with a missing wheel otherwise), one copy per data center used. Uploading from a Claude Code session runs at ~5 MB/s, ten to twelve minutes per volume.
- **A worker can take the job and then not progress.** Run 34873923702 (0.6B, 2026-09-14) was taken by an RTX 4090 worker at 17:39 whose route to PyPI ran at roughly 100 KB/s: after 2 h 47 min its log held nothing but the environment install (`uv run` builds the tree's venv from the lock before anything else runs; ~3 GB of wheels, two minutes on a normal host), nineteen small wheels done and every large one still in flight. The install completed after 3 h 55 min and the pipeline then ran normally (19.5 min, results bit-identical to a second worker's), so a slow host is a delay, not a corruption. The runner bounds only the queue (`--queue-timeout-minutes`) and the wall clock, by choice: whoever requested the run watches its live log (`scripts/runpod_log.py <run id>`, above) against the milestones of the previous run of that model, i.e. the install's download lines give way to the pipeline's first `INFO` line within ~3 min of `IN_PROGRESS`, the first task's few-shot line within a few minutes more on a warm model cache, task lines at the previous run's cadence, results within the previous wall time plus a third. A run behind those is a worker problem until shown otherwise, and it is cancelled from the Actions UI (a session's GitHub token cannot cancel a run, and the RunPod key in the session is read-only); the next request lands on a fresh worker.
